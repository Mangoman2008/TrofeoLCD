# 预烘焙 JPEG 序列（在这块屏上放"视频"）

> 结论先说：Trofeo Vision 9.16 只认**整帧 JPEG**（无 H.264、无等时端点、固件不支持局部刷新），
> 所以这块屏上的"视频"只能是**逐帧 JPEG**。把视频离线烘成 JPEG 序列、运行时**零编码**直推，
> 能把帧率从"实时渲染+编码"的 ~2.4fps（受策略限速）/ ~6fps（工作量上限）
> 抬到 **11.6fps（48KB/帧）～ 7.0fps（73KB/帧）**，且推帧耗时实测与模型吻合。
>
> 两种喂帧方式：**预载**（一次全拉进内存，绝不抖动）与**流式**（环形缓冲边播边拉，
> 只占窗口大小的内存、起播快，长片用）。实测两者帧率一致，流式 0 欠载。

## 〇、界面入口

App 页面「主题」那一行的下面新增了一行「序列」：`面板抓帧 / 仪表盘视频 / 长片 600 帧 /
流式 / 停止`，右侧显示一行状态（如 `序列 ● dash-q60 预载 37/120 · 11.4fps · 72ms/帧`）。
预设地址写在 `pages/Index.ets` 的 `SEQ_PRESETS`（对应本机 `seq_server.py` 的目录）。

## 一、为什么值得做

本机实测（2026-10-14，真机屏 0416:5408）：

| 路径 | 每帧成本 | 说明 |
|---|---|---|
| 实时渲染+编码（默认） | render 3ms + **encode 55～164ms** + push 71～134ms | 编码是大头，且随主题复杂度暴涨 |
| 预烘焙序列（本方案） | **只有 push**（71～134ms） | 帧是现成 JPEG，字节原样推出去 |

每次 4096B `bulkTransfer` 有 **~5.5～6.9ms** 固定开销（受控 A/B 实测 5.5/6.7ms，
与 `LcdUsb.ets` 注释、HANDOFF 记录一致），所以帧率 ≈ 1000 /（写次数 × 5.5ms + 3ms ACK）。
**字节数就是帧率**：48KB ≈ 13 次写 ≈ 72ms/帧 ≈ 11.6fps；73KB ≈ 19 次写 ≈ 134ms/帧 ≈ 7.0fps。

## 二、怎么用

```bash
# 1) 烘一段序列（默认按面板物理方向旋转 180°，必须与实际安装方向一致）
python3 tools/make_seq.py --src docs/V4版-屏上抓帧.png --out ~/.cache/seq-root/rich \
        --frames 120 --fps 12 --q 60
#    · Ken Burns 推近+横移 + 一条扫过的亮带（保证帧间有变化、肉眼能看出在播）
#    · --bar 0 去掉亮带（字节更省）；--no-rotate 不旋转
#    · 已有 1920×462 图批量转：tools/frames_to_seq.py --src-dir <dir> --glob 'f*.jpg'

# 2) 起本机 HTTP 服务（App 里没有文件 IO，走已验证的 localhost HTTP 通路）
python3 tools/seq_server.py --dir ~/.cache/seq-root --port 8899

# 3) 播放 / 调帧率 / 停止（都是运行时，随时可回滚）
curl "http://127.0.0.1:54546/set?seq=http://127.0.0.1:8899/rich"   # 开始（先取清单再拉帧）
curl "http://127.0.0.1:54546/set?seqfps=60"                        # 帧率（不设 = 用清单里的）
curl "http://127.0.0.1:54546/set?seqlimit=120"                     # 预载：最多拉多少帧（上限 480）
curl "http://127.0.0.1:54546/set?seqstream=1&seqwin=24"            # 流式：只占 24 帧内存
curl "http://127.0.0.1:54546/set?seq=off"                          # 停止（还原帧间隔、恢复常规渲染）
```

`/diag` 里的取证字段：`seqState / seqMsg / seqBase / seqName / seqCount / seqCursor /
seqPushed / seqErrors / seqLoadMs / seqFps / seqPushMs / seqFpsSet / seqLimitSet / seqLoop /
seqStream / seqWin / seqBufFill / seqBufCap / seqAhead / seqFetched / seqUnderruns /
seqSelfTest`。`/frame.jpg` 在播放时就是**当前推给屏的那一帧**。

### 预载 vs 流式

| | 预载（`seqstream=0`，默认） | 流式（`seqstream=1`） |
|---|---|---|
| 内存 | 全部帧（`seqlimit` 帧 × 每帧字节） | 环形缓冲 `seqwin` 帧（默认 24，约 1.2MB） |
| 起播 | 要等拉完（480 帧 ≈ 3.6s） | 0.14～0.35s（先预取满窗口就播） |
| 抖动 | 不会（帧都在内存里） | 不会（实测 0 欠载；抓帧 ~1.5ms/帧 vs 推帧 ~90ms/帧） |
| 适合 | 短片/要求绝对稳定 | 长片、任意长度 |

### 极速模式（`/set?seqburst=1`，界面「极速」按钮）

帧循环是 `tick → setTimeout(间隔) → tick`，**间隔是加在推帧耗时之外的**：
movie 序列（41.8KB/帧、推帧 56ms）按 60fps 节流时只有 11.4fps，因为每帧还多等 16ms。
`seqburst=1` 把间隔压到 1ms，等于"USB 有多快推多快"：

| 序列 | 帧字节 | 写次数 | 节流（16ms 间隔） | **极速** |
|---|---|---|---|---|
| movie（狮子王 4K 烘的 120 帧） | 41.8K | 11 | 11.4fps | **20.5fps** |
| dash（仪表盘抓帧） | 48.0K | 13 | 11.6fps | **16.8fps** |
| rich（面板抓帧 + Ken Burns） | 67.0K | 17 | 7.0fps | **10.3fps** |

极速 + 流式（600 帧长片、窗口 24）实测 13.3fps、**0 欠载** —— 抓帧压力（~2ms/帧）
远小于推帧（90ms/帧），流式在极速下也跟得上。

**半窗滞回**：抓帧只在窗口掉到一半以下时才成批补。若每推一帧都去补一次，
抓帧会变成"每帧插一次 HTTP"，同一个 JS 线程里的 HTTP 回调会拖慢正在 await 的
`bulkTransfer` —— 实测推帧耗时从 91ms 抬到 182ms（win=8 那组）。加滞回后该现象消失。


## 三、实现位置

| 文件 | 作用 |
|---|---|
| `entry/src/main/ets/service/SeqPlayback.ets` | 纯逻辑：清单解析、帧间隔、游标推进、URL 拼装 + 19 项离线自检（`seqSelfTest`） |
| `entry/src/main/ets/service/LcdService.ets` | `tick()` 最前面一条分支：序列播放时**绕开渲染与编码**，只 `sendJpeg(帧字节)`；`/set?seq*` 三个开关；`/diag` 字段 |
| `tools/make_seq.py` | 一张图 → Ken Burns 序列 + manifest.json（含字节/写次数/预估 fps） |
| `tools/frames_to_seq.py` | 一批 1920×462 图 → 序列（只重编码 + 旋转） |
| `tools/seq_server.py` | 本机 HTTP 服务（禁缓存、只绑 127.0.0.1） |
| `tools/build_seq.sh` | 在独立副本（`.trofeolcd-seqbuild`）里构建签名 HAP，不碰源码工程与别的构建目录 |

manifest.json 字段：`name/count/fps/w/h/pattern/loop/rotate180/q/bytes*/writesAvg/estPushMsAvg/estFpsCap`。
帧文件名由 `pattern`（默认 `f%04d.jpg`）决定，从 **0001** 开始。

## 四、实测（2026-10-14，真机屏）

| 序列 | 帧字节 | 写次数 | 实测推帧耗时 | 不设上限时实测 fps | 错误 |
|---|---|---|---|---|---|
| `dash-q60`（本机仪表盘抓帧，24 张循环） | 47.6～48.1K | 13 | 71～73ms | **11.4～11.6** | 0 |
| `panel-rich`（面板抓帧 + Ken Burns + 亮带，q60） | 63.8～76.6K | 17～19 | 93～134ms | **7.0** | 0 |

流式 vs 预载（同一段 600 帧长片，48KB/帧；安静时段背靠背测的对照）：

| 配置 | fps | 推帧耗时 | 欠载 | 起播 | 备注 |
|---|---|---|---|---|---|
| 预载 480 帧 | 9.66 | 93.0ms | 0 | 3.58s | 内存里压着 480 帧 |
| 流式 win=24 | 9.64 | 90.7ms | 0 | 0.35s | 内存只有 24 帧 |
| 流式 win=8（加滞回后） | 最高 9.38 | 126ms | 0 | 0.14s | 加滞回前只有 7.2fps（推帧被 HTTP 插队拖到 182ms） |

> 这台机器上还有别的会话在改同一个工程、反复重编译并重启 App，所以**噪声很大**：
> 忙时同一配置只有 4.6～7.8fps。上表取的是安静时段/多次测量里的最好值（吞吐上限）。

- 载入 120 帧（~8MB）走 localhost HTTP 只要 **1.1～1.4s**，之后播放不再需要网络。
- `seqPushMs ≈ tickMs`：证明这条路径确实只剩 USB 一段成本（渲染/编码都被绕开了）。
- 停止后原路径立即恢复：`forceIntervalMs` 还原为 0、`seqState=done`，下一帧照常渲染推屏。

### 踩到的坑：帧率要设"高"，不要设"低"

播放节奏是 `tick + forceIntervalMs`（`loop()` 里的 `setTimeout` 在 tick 之后），
所以设 `seqfps=12` 并不会把一帧的成本摊进 83ms，而是**在推帧耗时之外再加 83ms 等待**：

| `seqfps` | 实测 fps（dash，48KB） |
|---|---|
| 60（≈不设上限） | 11.4 |
| 30 | 9.2 |
| 20 | 7.3 |
| 15 | 7.0 |

**播放请把 `seqfps` 设高（例如 60 / 120），让它跑满 USB 上限**；想降帧率省电再往下调。

## 五、边界与注意

1. **旋转要在烘焙时做掉**：面板相对画布是 180°（本机 `rotate180=true`）。序列帧若没预旋转，
   屏上就是倒的 —— 而运行时旋转意味着"解码 + 重编码"，正好抵消了本方案的意义。
   `make_seq.py` / `frames_to_seq.py` 默认已旋转，manifest 里记 `rotate180: true`。
2. **内存**：预载模式一次拉 `seqlimit` 帧（默认 120，上限 480 ≈ 8～32MB）；流式只占 `seqwin`
   帧（默认 24 ≈ 1.2MB）。放长片请用流式。
3. **不改动原路径**：`seq` 为 `off/done` 时 `tick()` 走原来的渲染+编码分支，行为与之前一致。
4. **这条屏的硬上限仍在主机栈**：每次 4KB 写 ~5.5-6.9ms（桌面 libusb 同屏同写模式实测 24fps，
   即每次 ~1.7ms）。要再往上走只能减少写次数（省字节/降分辨率）或换原生 USB 通路。
5. 帧率要设**高**（`seqfps=60`）：播放节奏是 `tick + forceIntervalMs`，设低了是在推帧耗时之外
   再加等待（60→11.4fps、30→9.2、20→7.3、15→7.0）。
6. 详细推导与原始数据：`.verify/video-seq/报告-预烘焙序列验证.md`。

## 六、把真实视频（MP4/MKV）烘成序列

**本机可以直接烘，不需要另找 PC。** 关键事实：

- 这台 HarmonyOS PC **不允许 exec 用户态二进制**：`ffmpeg.bin`（静态 aarch64）复制到可写目录
  后仍 `Permission denied`，连 `cp /bin/echo` 之后执行也是 EACCES。所以"下载个 ffmpeg 来用"这条路是堵死的。
- 但它**允许 dlopen 共享库** —— Python 的 **PyAV** 轮子自带整套 ffmpeg 共享库
  （libavcodec 63 / libavformat 63 / libswscale 10 …），**进程内解码**，不 exec 任何东西。
  装一次即可：`python3 -m venv ~/.venvs/mp4seq && ~/.venvs/mp4seq/bin/pip install av pillow`

```bash
~/.venvs/mp4seq/bin/python tools/mp4_to_seq.py \
    --src movie.mkv --out ~/.cache/seq-root/movie \
    --start 660 --duration 12 --fps 10 --q 55 --name lionking-12s
#    · 等比铺满 1920×462 后居中裁切（不变形），默认预旋转 180°
#    · --fps 就是序列帧率（这块屏再高也推不动，10~12 足够）
#    · 产出 f0001.jpg… + manifest.json（含源编码/分辨率/时长、字节统计、预估帧率）
```

实测（本机，2026-10-14）：

| 源 | 编码/分辨率 | 时长取用 | 输出 | 耗时 | 每帧字节 | 预估上限 |
|---|---|---|---|---|---|---|
| USB 摄像头录像 | h264 2560×1440 | 1.0s 起 2.3s | 16 帧 @12fps | ~4s | 79.7KB | 8.4fps |
| 狮子王 4K 正片 | **hevc 3840×2160** | 600s 起 5s | 40 帧 @8fps | ~18s | 39.6KB | 17.2fps |

4K HEVC 解码约 0.45s/帧（本机软解），烘 12s 素材（120 帧）约 1 分钟 —— 一次性代价，
换来的播放是零编码直推。**照片类内容的体积在 40～80KB/帧，对应 8～17fps 的播放天花板**。
