## 2. ⑥b 加宽档是什么（随时可再开）

用户原话：「把 USAGE 隐藏，打印机把它的横向空间占了，按方案 6b 看看」。
**开启方式：改 `entry/src/main/ets/common/Theme.ets` 两行**

```ts
static readonly usPanelVisible: boolean = false;   // 原 true：隐藏 USAGE，空间让给打印机
static readonly prW: number = 448;                 // 原 L.panelWidth(274.4)：448 = 源画布纵向像素数
```

改完要跑：`python3 tools/layout_check.py --theme=0` → `bash tools/cli_build.sh`
→ `hdc -t 127.0.0.1:40601 install -r .build-output/entry-default-signed.hap`
→ `aa force-stop/start com.dsh.trofeolcd` → `curl http://127.0.0.1:54546/diag`

## 3. 源画布 1:1 的真实约束（这一轮的硬结论）

| 项目 | 数字 |
|---|---|
| 物理屏 | 1920 × 462（**462 是纵向**；14 边距 ×2 → 可用 434） |
| 源画布（Dotii / 拓竹 AMOLED） | 368 宽 × 448 高 |
| 纵向差 | 448 − 434 = **14 行**，所以源画布再怎样也做不到「整幅 1:1 全露」 |
| 横向差 | 源只要 368，而中卡行有 1868 → **横向从来不是瓶颈** |
| 等宽档格子只占整屏高度 | 196 / 462 = **42%**（这是"浪费分辨率"的真正来源） |

结论：想要源画布 1:1，必须让打印机格**纵向吃满 434**；而吃掉整列会让整屏只剩
4 个面板（观感见上）。现在的取舍是：**保住 5 面板观感，源画布按格子缩放**。

### 6.2 帧率真相（重要，别再把 3fps 当硬件极限）

- **真凶是内容签名**：`LcdService.contentSignature()` 里原来只有"分钟"和 `printerSubPage()` 与游戏有关，
  而打砖块在 `printerSubPage()` 里恒定返回 0 → 球在动但签名不变 → **每帧都被判"没变化"跳过**
  （实测 `skippedFrames=999`，屏上只剩 10 秒心跳帧）。修法：签名加 `pong=<tick|ballX|ballY|bricksBroken>`。
- 修完实测上限：**7～8 fps 封顶**，每帧 render 1.6~2.8 + encode 48~65 + push 47~148 ≈ **110ms**；
  间隔从 500ms 压到 17ms，fps 只在 3.8→7.1 之间变，说明瓶颈是**串行流水线**，不是定时器。
- 已知的下一步（未做）：**编码与推送流水线化** → 理论上限 `max(encode,push)≈60ms` ≈ 16fps，实际约 10~12fps。
- **别把 JPEG 质量调低**：q=0.6/0.4 实测编码反而变慢到 136/204ms（走了慢速回退路径），保持 0.85。
- 静态主题仍在 idle 档 500ms/2fps（设计如此）；打砖块现在跑 30Hz。

### 6.3 rot180 的结论（用户问过）

设备握手自报 `rotateDeg=180`，`rotMode=0` 跟随握手 → 必须转。它是渲染开头**一次画布变换**
（`translate+rotate`），不额外拷贝像素、不改变 1920×462 输出，成本可忽略。
运行时验证：`/set?rot=off` 屏上立刻上下颠倒。相关代码：`LcdService.rotateNow()` / `rotMode`（0 跟随/1 强开/2 强关）。

### 7.2 三个关键工程结论

1. **漏光补偿（用户报"右下角漏光严重"）**：`Chrome.vignette()` 椭圆径向渐变，
   按**旋转后**的物理角定位（`rotate180=true` 时缓冲区角码要取反，否则压到左上角 —— 实测踩过）。
   `/set?vig=0..100`、`/set?vigreach=N`。实测 vig=70 时右下角 −8.3、左上角 +0.2（不误伤）。
2. **JPEG 4:2:0 色度抽样**：本机编码器输出 SOF0 `[C1 2x2]`，**纯蓝 #0000FF 解码后几乎归零**、
   纯青 #00FFFF 归零。已做**源色预补偿**（砖块蓝 → `#3A55E0`、绿 → `#20E020`、青 → `#30D8E0`…），
   实测蓝砖 0 → 1362 像素。`/set?fws=100` 是色卡标定页。
3. **帧率天花板 ≈ 8fps**：每帧 render 2 + encode 48～65 + push 47～80 ≈ 110ms，串行流水线。
   间隔压到 17ms 也只到 7fps；**且会打死 USB 端点**（`bulkTransfer -1`、屏卡开机画面、diag 无响应，
   只能 force-stop 重开应用）。已钉死 `MIN_PUSH_INTERVAL_MS = 120`、`writeBatch = 1`、`wsize ≤ 4096`。

### 7.3 协议调研结论（子代理，带出处）

- 屏内固件解码 JPEG 约 **1s/100KB**，解码期间帧被**静默丢弃**（trcc-linux issue #251）
- **不支持原始帧**（PM=65 不在 RGB565 白名单）、**不支持局部刷新**（LY 协议只有 1 个子命令）
- 官方软件自己只有 **15/24 fps** 档位；同款屏社区最好成绩 **24fps**（sensorpanel）
- USB 不是瓶颈（40KB×60fps 只需 2.6 MB/s，链路能跑 30～40 MB/s）
- 推 462 vs 480 的「双重缩放」问题见 issue #248 → 已加 `/set?frh=` 开关待实测
