## 3. C 组：性能优化（都有安全论证 + 字节级回归背书）

### C1. LY 分块流缓冲复用（每帧 ~2-3MB 垃圾 → 0）
`entry/src/main/ets/usb/LyProtocol.ets`
- `buildChunkStream`：模块级 `chunkStreamBuf` 复用（容量不足才扩），返回 `subarray(0, need)` 精确视图；
- 逐字节拷贝 → `out.set(jpeg.subarray(...), off + CHUNK_HEADER_SIZE)` 批量；
- **残区清零**：`fill(0, residueFrom, need)` 一次覆盖尾块残区 + 补齐块（复用的 buffer 不是全 0，防上一帧字节残留）；
- `writeChunks` slice → subarray。
- 安全论证：调用面仅 `LcdUsb.sendJpeg`（stream 局部）+ SelfTest（同步用完即弃）；sendJpeg 严格单飞三护栏（普通推帧 pushInFlight、流水线 pushBusy 背压、序列推帧双护栏），bulkTransfer 同步完成 JS→native 拷贝。
- 回归：KAT FNV 逐字节一致（59/59）、600KB 往返逐字节一致（20/20，600000B→1212 块/152 写）。

### C2. 渐变缓存（0.2~1ms/帧）

## 5. C# 移交清单（本轮不动代码，供 Windows 虚拟机编译验证）

> `win/` 本机无法编译，以下三项已核实行号（win/ 未被本轮改动），建议下次在

### 中-8 `_dev` 句柄无互斥（LcdRunner.cs）
- `:72` `private WinUsb.LyDevice _dev;`
- `:127-131` `CloseUsbNow()` → `CloseUsb()`（置空 `_dev`）
- `:353-361` 推帧路径 `if (_dev != null && jpg != null) { ... WinUsb.PushJpeg(_dev, ...) }`
- 风险：UI 线程关 USB 与渲染线程推帧并发时，`_dev` 可能在 null 检查与使用之间被置空（TOCTOU）。
- 建议：`_devGate` 锁对象包住 CloseUsb/推帧两段；或 `_dev` 用 `Interlocked.Exchange` 取局部引用后再判空使用。

### 中-9 诊断字段无 volatile/Interlocked（LcdRunner.cs:99-101）
- `_frames/_sent/_errors`（long）、`_renderMs/_encodeMs/_pushMs/_quality`（double）、`_ack`（string）
- 跨线程读写（渲染线程写、诊断线程读），无 happens-before 保证；long/double 在 x64 上原子性靠运气（ARM64 上 64 位对齐读写通常原子，但规范不保证）。
- 建议：计数用 `Interlocked.Increment`，均摊值写入用 `Interlocked.Exchange`/`Volatile.Write`，或统一走一个加锁的 snapshot()。

### 低-11 `_requests++` 非原子（MiniHttp.cs:171）
- 多连接并发时丢计数（只影响诊断数字，不影响功能）。
- 建议：`Interlocked.Increment(ref _requests)`。
