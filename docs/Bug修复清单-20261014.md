## 一、已修（代码已改，待编译验证）

### H1 · USB 句柄/接口泄漏（严重：会导致"再也连不上，只能杀进程"）

- **位置**：`entry/src/main/ets/usb/LcdUsb.ets`（`open()` 握手分支 + `close()`）
- **原因**：`open()` 里 `this.pipe = connectDevice(...)` 之后才握手；握手失败时只把 `opened` 置 false
  就 `return null`，**pipe 未 closePipe、接口未 release**。下次 `open()` 因为 `opened=false`
  继续往下走，直接覆盖旧句柄 → 旧 pipe 永不释放、接口永久 claimed。
- **改法**：
  - 握手失败 → `Logger.w(...)` + `this.close()` 回滚后再 return null
  - `close()` 补清理：`iface / cfg / outEp / inEp / refs` 全部置空
    （原来只清 `pipe / opened / info`，下次会用旧 iface/端点操作已关闭的 pipe）

### H2 · 帧尾静默丢失（严重：花屏/黑屏/停在上一帧的根因）

- **位置**：`entry/src/main/ets/usb/LyProtocol.ets`（`writeChunks`）
- **原因**：`pos += ws`（按**整块大小**推进）而不是按**实际发送长度**。
  尾部 `size = min(2048, remaining)` 时，实际只发了 2048 字节、位置却推进了 `ws` →
  **尾部 `remaining - 2048` 字节被丢弃**（正是帧尾 4~8 个分块）。
- **触发条件（可算死）**：
  - 默认 `wsize=4096` + PID 0x5408：`remaining` 只能是 2048 → 恰好正确，**所以一直没暴露**
  - `/set?wsize=6144` 或 8192：`total=10240` 时实发 8192，**丢最后 2048B**
  - PID 0x5409 设备（分块数不补齐 4 的倍数）：`remaining=3584` → 丢 1536B
- **改法**：`size = min(ws, remaining)` 且 `pos += size`；LY 的"尾包 ≤2048"靠**循环继续拆**实现
  （而不是一次跳过）。默认路径行为不变（`remaining=2048` 时结果与原来一致）。
- **旁证**：这很可能就是之前偶发"画面不刷新、要重发才显示"的真凶 ——
  主机侧 `bulkTransfer` 全部返回成功，固件收不到帧尾就永远解不出那一帧。

### H3 · 内容签名先于推送提交（严重：旧画面 10 秒 / 告警帧永不显示）

- **位置**：`entry/src/main/ets/service/LcdService.ets`（`tick()` + 新增 `pendingSig` + `recordPushResult()`）
- **原因**：原来在 `sendJpeg` **之前**就 `this.lastSig = sig; this.lastPushMs = now`。
  推送失败、或被流水线背压跳过时，内容已被记成"推过了" → 最长 `HEARTBEAT_MS`(10s) 不再重推。
- **改法**：新增 `pendingSig`；`tick()` 只写 pendingSig；`recordPushResult(true)` 才提交
  `lastSig = pendingSig; lastPushMs = now`；失败时 `lastSig = ''`（下一轮无条件重推）。

### 已改的另外两处（我自己实测发现的）

- **`wsize` 上限钉死 4096**：`/set?wsize` 分支加 `Math.min(4096, ...)`（8192 实测会把 HAL 打进错误态）
- **漏光补偿角与旋转的关系**：`vigCorner()` 按 `rotateNow()` 取角（实测过四个角码，
  确认旋转时该压缓冲区**左上角**才能压到物理右下角）

### H4 · 停止推送后再也启动不了（严重：帧循环永久死锁）

- **位置**：`entry/src/main/ets/pages/Index.ets`（停止/启动按钮的 onClick）
- **原因**：`startService()` 开头有 `if (this.startCalled) { refreshStatus(); return; }` 守卫，
  但点「停止推送」时只把 `running=false`，**没复位 `startCalled`** → 再点「启动推送」直接
  命中守卫 return，`service.start()` 永不再次调用，帧循环永久死亡（只能 `/set?run=1` 或重启应用）。
- **改法**：停止分支加 `this.startCalled = false;`

### H5 · 渲染异常导致画布状态逐帧累积（严重：画面永久错乱）

- **位置**：`entry/src/main/ets/service/LcdService.ets`（`tick()` 的渲染段）
- **原因**：`ctx.save()` 与 `ctx.restore()` 之间隔着 ~200 行渲染分发，**没有任何保护**。
  任一主题渲染抛异常（字体串非法、`measureText`/`drawImage` 抛、数组越界）→ 异常冒泡到
  `loop()` 的 catch，**`restore()` 被跳过** → 变换/裁剪/`globalAlpha`/字体状态**逐帧累积**
  （每帧再 save、再叠一次 rotate+scale）→ 画面永久错乱，而不是只坏一帧。
- **改法**：整段渲染包 `try { ... } catch { 记 lastError + renderErrors++ } finally { ctx.restore(); }`；
  `FrameStats` 新增 `renderErrors` 计数（便于发现某主题在悄悄抛异常）。

### M4 · 主题 5 的漏光补偿画在缩放坐标系里（失效）

- **位置**：`entry/src/main/ets/render/ThemeDotii.ets`（`render()` 末尾）
- **原因**：`Chrome.vignette` 写在 `translate(X,Y) + scale(0.9333)` **之内**，而主题 4/6 都在
  `restore()` 之后调用；`LcdService` 又明确不为主题 5 兜底 → 补偿被缩到 0.9333 并平移到
  Dotii 框的角上，**物理右下角实际没被压到**。
- **改法**：把 `ctx.restore()` 提到 `Chrome.vignette(...)` **之前**。

### M7 · 状态胶囊文字溢出（中文状态词必现）

- **位置**：`entry/src/main/ets/render/ThemeDotii.ets`（`statusPill`）
- **原因**：底框固定 138×48，文字只测宽求居中起点、**不校验是否超出胶囊**；
  源里「监控未登录」≈190px、「密钥无效」≈152px，必然溢出。
- **改法**：先量文字，宽度取 `max(w, 文字宽 + 圆点 + 间隙 + 内边距)`。

### M12 · 主题轮播只会在 0/1/2 之间循环

- **位置**：`entry/src/main/ets/service/LcdService.ets`（主题轮播分支）
- **原因**：`this.theme = (this.theme + 1) % 3` → 永远轮不到主题 3~6（分页屏/打砖块/Dotii/固件仿真）；
  且 `lastThemeSwitch` 初值 0 导致"刚开轮播就立刻切一次"。
- **改法**：改 `% 7`（当前共 7 个主题）；`lastThemeSwitch === 0`（刚开启）时先只记起点不切换。

## 三、存疑（需实测，别盲改）

1. `ThemeFwSim.ets` 进度环的 `%` 位置依赖遗留的 `textAlign='center'`；`pct=100`（三位数）时可能与 `%` 压印 → 切到 OTA 屏看一眼
2. `Dashboard.ets` CPU 温度与电量**共用同一 y**；两端目前都写死 -1，属"靠注释维持的不变量" → 一旦桥端给温度就会压印
3. `LyProtocol.setWriteSize` 自身仍允许到 65536（只在 `/set` 分支钳了 4096）→ 需确认 UI/SelfTest 是否绕过
4. JPEG 长度恰为 496 倍数时会发一个 `dataLen=0` 的末块（参考实现同样）→ 设备是否容忍需实测
5. `LcdService.stop()` 未复位 `pushBusy/lastSig/skipped` → 停止再启动后首帧可能被跳过
6. 审计工具盲区（`canvas_shim.ts` 的 `save/restore` 不存 textAlign/baseline、`measureText` 忽略 bold、`clip` 空实现；`layout_check.py` 只比同面板、阈值 10%/6..22px/≥40px 全是盲区）→ M7/M9/M10 这类 bug 正是没被审到的分支

## 四、优化建议（性价比排序，未实施）

1. **渲染 try/finally**（同 HIGH 那条）—— 收益大、风险≈0，**建议明早第一个做**
2. **分块流 buffer 复用**：现在每帧 `new Uint8Array(≈120KB)` + `slice` 再复制 120KB ≈ 2MB/s 垃圾
   → 常驻 buffer + `subarray` 零拷贝，省 1~3ms/帧 GC 抖动（`wbatch=1` 下安全）
3. **渐变缓存**：`background` 每帧 2 个 + `vignette` 1 个 + `sparkline` 每曲线 1 个，参数都是常量
   → 按 key 记忆化，省 0.2~1ms/帧
4. **修好并开启 `encodeFast`**：`toDataURL → base64 → decodeSync` 往返约 20~25ms/帧
   → 帧成本 110 → ~90ms，为下调 120ms 下限留空间（ROM 相关，有回退护栏）
5. **按主题分档 JPEG 质量**（文字 0.9+ / 游戏 0.8）并去掉主题 5 的全局提档 → 直接降线上字节
6. **抽 `ThemeRuntime` 注册表**（`reset/prepare` 钩子，切主题统一调用）→ 把"切主题要不要重置状态/恢复质量"
   变成结构性保证，根除上面 M2/M14 一类问题；也能给 1497 行的 `LcdService` 减负
7. **审计工具补强**（见三·6）→ 把布局类 bug 前移到离线检出
