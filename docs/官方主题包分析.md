# 官方 1920×462 主题包分析（一手证据）

> 来源：`~/.cache/trcc/repos/thermalright-trcc-linux/src/trcc/data/theme1920462.7z`（204 KB）
> 与 `theme4621920.7z`（9.55 MB，竖版）
>
> **怎么解出来的**（本机 `7zz` 是 glibc 版、在 musl 上跑不了，也没有 py7zr）：
> 用 openEuler 虚拟机（`user@172.16.105.2`，有 `dnf`）装了 **p7zip**：
> ```
> ssh user@172.16.105.2 'sudo -n dnf install -y p7zip'      # 装出 /usr/bin/7za
> scp <theme>.7z user@172.16.105.2:~/trcc7z/
> ssh user@172.16.105.2 'cd ~/trcc7z && 7za x -y theme1920462.7z -ot462'
> ```
> 解出来的成品已同步回本目录：[官方主题462/](官方主题462/)（5 套 × 4 个文件）
>
> 顺带：本机也写了一个纯 Python 的解析器 [tools/extract_theme7z.py](../../tools/extract_theme7z.py)
> （用 Python 自带 `lzma` 解 LZMA2+BCJ，已能解出编码头），但那批包里**没有常规文件条目**，
> 走标准工具更省事 —— 脚本留作参考与离线校验。

```

  Theme1/{ Theme.png, 00.png, 01.png, config1.dc }
  Theme2/{ … }   Theme3/{ … }   Theme4/{ … }   Theme5/{ … }
```

| 文件 | 1920×462 横版大小 | 作用（对照 trcc 的主题格式定义） |
|---|---|---|
| `Theme.png` | ~40 KB | 主背景图（1920×462，8-bit RGBA） |
| `00.png` | ~4.6 KB | 动画帧 0（差异很小，应是"元素高亮/呼吸"那类叠加） |

## 二、设计风格（视觉模型读图，一手结论）

5 套主题**布局与字体完全一致，只换配色**。以 Theme1 / Theme2 为例：

| 区块 | 位置（画面百分比） | 内容 |
|---|---|---|
| 左卡片 | x 7–26%、y 10–88% | `CPU / 50℃ / 1% / 3593MHz` |
| 中央 | x 44–56% | 灰色大字时间 `17:03`（y 19–38%）+ `星期六 / 2025/05/17`（y 58–80%） |
| 右卡片 | x 74–92%、y 10–88% | `GPU / 44℃ / 3% / 10MHz` |

**关键特征（与我们现在的风格正好相反）**：

- **浅色底**：Theme1 薄荷绿 `#98F5A9` + 淡黄绿卡片 `#E9F4A0`；Theme2 淡黄绿底 `#DFF2A0` + 橙色卡片 `#F79A4D`
- 圆角卡片 + 投影，居中大时间，两侧对称信息卡
- **没有圆环、没有曲线、没有图表** —— 纯文字/数字排版
- 我们的 7 个主题全是**深色霓虹/仪表盘风**（深底 + 青蓝紫强调 + 环形曲线）

→ 可做的事：加一个"**官方浅色风**"主题（三栏卡片 + 居中大时间），作为现有深色风格的对照选项。
素材就在本目录，可直接当背景底图用（RGBA PNG，透明区可让我们的文字透出）。

## 三、分辨率：**官方横版就是按 480 行做的**（一手证据）

解出来的 `Theme.png` **全部宽高比 = 1920×480**，而面板玻璃约 468 行、固件内部帧缓冲 480 行。

这印证了 trcc-linux issue #248 的说法，也修正了本项目一直推 **462** 的假设：
**推荐把推帧高度改成 480**（`/set?frh=480`，代码已有开关）。理由：

| 推 462 | 推 480 |
|---|---|
| 固件要 462→480→468 **两次缩放** → 画面发虚 | 只需 480→468 **一次缩放** |
| 纵向少 18 行像素 | 用满固件缓冲 |

**这个开关已就绪，但还没上屏实测**（等屏重新枚举）。判定方法：切到主题 6 的打砖块时钟屏
（`/set?fws=8`，白边细字最多），分别在 `frh=0`（462）与 `frh=480` 下抓帧，比文字边缘梯度中位。

## 五、素材的两层结构（实测，容易踩）

官方每套主题的 PNG **不是一张图**，而是两层：

| 文件 | 不透明像素 | 内容 |
|---|---|---|
| `00.png` | **100%** | **纯背景色**（整幅同色，无卡片、无文字） |
| `01.png` | **28%** | **卡片叠加层**：背景透明，只有两圆角卡片 + 柔和投影 |
| `Theme.png` | 100% | 官方的**预览图**（背景 + 卡片 + 示例文字 `CPU 50℃ 1% 3593MHz`） |

**踩过的坑**：我一开始把 `Theme.png`（带示例文字）或 `00.png`（纯色）当底图 ——
前者会和实时数字重影，后者根本看不到卡片。
正确做法是 **先铺背景色、再叠 `01.png` 卡片层**，然后在卡片位置画自己的实时数字。

实测验证（本机渲染帧 vs 官方原图，RGB 逐点比对）：
```
背景 本机 (151,255,168)  vs 官方 (150,255,168)   ✅
卡片 本机 (238,247,164)  vs 官方 (238,247,163)   ✅
```

## 七、附带结论：462 vs 480 实测（结论与第三方推断相反）

用打砖块时钟屏（白边细字最多）分别推 462 与 480 抓帧比对：

| 设定 | 实际帧 | 边缘样本 | 中位 | 90 分位 |
|---|---|---|---|---|
| `frh=0`（设备报的 462） | 1920×462 | 3426 | **41** | **161** |
| `frh=480` | 1920×480 | 3353 | 37 | 138 |

→ **480 反而更糊**（中位 41→37、90 分位 161→138），且画面没有报错也没有明显裁切。
结论：**以设备握手自报的 462 为准**（它比 issue #248 的第三方推断更权威）。
`/set?frh=480` 开关保留，随时可复测。
