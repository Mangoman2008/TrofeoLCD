## 一、致命 / 高危

### 【致命-1】ArkTS 的 JPEG 上限还是 650000，而 C# 侧已按实测降到 450000 —— 同一份协议两套真源，超限帧会被固件静默丢弃

**位置**
- `entry/src/main/ets/usb/LyProtocol.ets:17`
- `entry/src/main/ets/usb/LyProtocol.ets:238`（`maxJpegSize()`）
- `entry/src/main/ets/service/LcdService.ets:2116`（降质阶梯的触发条件）
- 对照：`win/src/Ly.cs:50`、`win/src/SelfTest.cs:121`

**证据**

```ts
// entry/src/main/ets/usb/LyProtocol.ets:17
const MAX_JPEG_SIZE: number = 650000;
```

```csharp
// win/src/Ly.cs:42-50
/// 单帧 JPEG 上限。450000 有两个独立来源 + 一个硬件实测锚点：
///   · 厂商反编译 USBLCDNEW.dll / ImageToJpg 的 max_frame_bytes 常量 = 450000（trcc 引用）
///   · 同型号开源驱动 trofeo-lcd（Rust）MAX_FRAME_BYTES = 450_000
///   · 真机实测：~360 KB 正常显示，~570 KB 被固件忽略
/// 旧值 650000 抄自 MacTR —— 那个项目声明了 maxJPEGSize 却从不检查它，
/// 650 KB 落在"被忽略"区间里，属于没有依据的值。
public const int MaxJpegSize = 450000;
```

```ts
// service/LcdService.ets:2116  降质阶梯只在超过上限时才启动
if (fast.length > LyProtocol.maxJpegSize()) { ... }
// else 分支（toDataURL 路径）同理：
// LcdService.ets:2144
if (bytes.length <= LyProtocol.maxJpegSize() || quality <= MIN_QUALITY) { break; }
```

**触发条件**：画质档设到 `quality`（默认 0.85，用户可 `/set?q=1`），一帧 JPEG 落在 450000–650000 之间 ——
Android/鸿蒙侧的判断认为“没超限、不用降质”，照常推出去，而固件在 450 KB 以上**直接忽略这一帧**。

**影响**：`stats.sent` 正常增长、`sendJpeg` 返回 true、`/diag` 全绿，**屏上是旧画面**。
这正是“画面偶尔不刷新/需要重发才显示”最难定位的那一类症状：所有应用侧指标都自证成功。

**为什么至今没暴露**：C# 侧已经把 450000 硬编码进它的自检（`win/src/SelfTest.cs:121` `Eq("MaxJpegSize=450000", Ly.MaxJpegSize, 450000);`），
但 ArkTS 自检里**没有这一项**（`entry/src/main/ets/usb/SelfTest.ets` 全文无 `MaxJpegSize`），
所以 38/38 的“协议自检全通过”从来没覆盖到这个常量。两份实现从此各说各话。

**建议修法**：把 `MAX_JPEG_SIZE` 改成 `450000`，在 `usb/SelfTest.ets` 里补一条与 C# 同名的断言
（`Eq('MaxJpegSize=450000', LyProtocol.maxJpegSize(), 450000)`），并在 `contentSignature` 之外
把“本帧字节数/上限”也暴露进 `/diag`（`jpegBytes` 已有，加一个 `jpegLimit` 即可一眼看出逼近程度）。

### 【致命-2】`printerSubPage()` 对槽位 2 及以上恒返回 0，导致内容签名不随 AMS 子页变化 —— 打印机格会“停在某一页不动”

**位置**
- `entry/src/main/ets/render/Dashboard.ets:1420-1434`（真源 A：内容签名）
- `entry/src/main/ets/render/Dashboard.ets:641`（真源 B：实际渲染）
- 消费方：`entry/src/main/ets/service/LcdService.ets:1153`（`prn=${Dashboard.printerSubPage()}`）

**证据**

```ts
// render/Dashboard.ets:1420
static printerSubPage(): number {
  const t = Date.now() % (Dashboard.PRINTER_CAROUSEL_MS * 3 + Dashboard.PRINTER_GAME_MS);
  const slot = Math.floor(t / Dashboard.PRINTER_CAROUSEL_MS);   // 0..7（50s 之后都算打砖块）
  if (slot === 0) { return 0; }
  if (slot === 1) { return 1; }
  if (slot === 2) { return 2; }
  // 槽 3/4（表情）与 5（打砖块）在 B 线实现前先回落到概览，不画空白
  return 0;
}
```

```ts
// render/Dashboard.ets:641  真正决定画面的是这一行，用的是 **% 4**
const sub = Math.floor(Date.now() / Dashboard.PRINTER_CAROUSEL_MS) % 4;
```

**触发条件**：主题 0、高亮到打印机格、且**其余内容在这段时间内没有变化**（内容签名不变 + 距上次推帧 < 3s 心跳）。

**影响**：
- 两个函数的“槽位 = 时间 / 10s”根本不带同一个取模基数：`% 4`（渲染）对 `% 8 + 30s 游戏槽`（签名）。
  签名在前 30s 返回 0/1/2、之后恒为 0；渲染则按 `% 4` 每 10s 循环。
- 于是**签名压根不追踪子页变化**。`sub` 从 1 走到 2（AMS 托盘页）时，签名里的 `prn=` 恰好是 0→2（会重推，能画上），
  但 `sub` 从 2 走到 3、从 3 走到 0 时签名不变 —— 屏上那 20 秒**停在 AMS 页**，底部 6 个指示点也停在 AMS 的位置。
- 由于 3 秒心跳（`LcdService.ets:1795`）会定期强制重推，观感是“大部分时间能跟上、偶尔卡一两拍”，
  属于最难复现也最容易被当成“屏端固件丢帧”的那类问题。
- 顺带：`PRINTER_SLOTS = 6`、`printerPanel` 只实现子页 0/1/2（`% 4`），
  指示点有 6 个但最多只有 4 个能被点亮。`HANDOFF-打印机格复刻.md:76-77` 已声明槽 3/4/5 未实现，
  所以“未实现”本身不是缺陷 —— **缺陷是签名与渲染用了两套不同的槽位算法**。

**建议修法**：把子页算法收敛成**唯一一个纯函数**，让签名与渲染都调它：

```ts
/** 唯一的槽位真源：渲染与内容签名都必须调它 */
static printerSlot(): number {
  return Math.floor(Date.now() / Dashboard.PRINTER_CAROUSEL_MS) % 4;
}
```
`printerPanel` 改用 `Dashboard.printerSlot()`，`printerSubPage()` 直接删掉（或改成它的别名），
`PRINTER_SLOTS` 收敛为 4（与指示点循环共用）。

### 【高危-3】看门狗把“卡住”和“推送还没返回”混为一谈，会在传输中途硬关 USB 句柄

**位置**
- `entry/src/main/ets/service/LcdService.ets:124-129`（看门狗字段与注释：`lastOkPushMs` + `STALL_MS`）
- `entry/src/main/ets/service/LcdService.ets:1748-1756`（看门狗判定与动作）
- `entry/src/main/ets/service/LcdService.ets:2202`（同步推帧，`await` 期间 `lastOkPushMs` 不会更新）
- `entry/src/main/ets/usb/LcdUsb.ets:363-399`（`sendJpeg`，错误时自己也 `close()`）

**证据**

```ts

    && Date.now() - this.lastOkPushMs > LcdService.STALL_MS) {
  Logger.w(`看门狗：${LcdService.STALL_MS / 1000}s 没有成功推帧，主动断开重连`);
  this.usb.close();          // 1751 —— 不看有没有在途传输
  this.lastOkPushMs = 0;

  this.usbRetryTs = 0;        // 立刻允许下一次打开尝试
  this.lastError = '推送卡住，已自动重连';
}
```

```ts
// service/LcdService.ets:2202  下面的 await 期间，看门狗条件依然成立
const ok = await this.usb.sendJpeg(jpeg);
```

```ts
// usb/LcdUsb.ets:396  传输异常时 sendJpeg 自己也关一次
this.close();
```

**触发条件**：`STALL_MS = 12000`（`LcdService.ets:130`）。一次推帧要 11~25 次批量写（`usb/LcdUsb.ets:376-388`），
每次 5s 超时（`usb/LcdUsb.ets:379`）。当端点进入错误态时，单帧耗时可以从 ~55ms 涨到**秒级甚至几十秒**
（`usb/LcdUsb.ets:355-359` 的事故记录里就有 push 34ms → 1540ms 的先例）。

**影响**：`this.usb.close()` 把 `pipe / iface / outEp / inEp` 全部置 null（`usb/LcdUsb.ets:416-425`），
而在途的 `bulkTransfer` 仍在跑。两种情况都会出现：
- 传输返回负值 → `sendJpeg` 内 `catch` 再调一次 `close()`（幂等，无害）；
- 传输“成功”返回 → `recordPushResult(true)` 被调用，`lastPushMs/lastOkPushMs` 被写成“刚刚成功”，
  **把看门狗重新喂饱**（`LcdService.ets:2676-2677`），而这一帧其实写入了一个已经关闭的 pipe —— 屏上什么都没变。
  这就制造出“应用侧 sent 在涨、屏没画面、usbOpenCount 恒为 1”的那个已知症状。
- 更边缘的：`close()` 与在途 `bulkTransfer` 同时操作同一 HAL 句柄，把端点打进错误态的概率变高。

**建议修法**：
1. 加在途标记，让看门狗不打断在途传输：
   ```ts
   private pushInFlight: boolean = false;   // sendJpeg 前置位、finally 清位
   ...
   if (this.usb.isOpen && !this.pushInFlight && this.lastOkPushMs > 0 && ...) { ... }
   ```
2. 或者把看门狗判定改成“距上次**尝试**推帧”而不是“距上次**成功**推帧”，
   并在 `close()` 后把闸门关到“至少等当前帧结束”（例如记一个 `usbEpoch`，`sendJpeg` 返回时校验 epoch 已变则丢弃结果）。

   按钮高亮与实际主题出现一帧错位。这条比第 1 条轻，但同样是“两处真源”。
3. `Logger.i(...)` 里的三元表达式只区分 1 和其余，主题 2..15 全被记成“仪表盘”—— 排障日志会误导。

**建议修法**：
- `themeApply()` 里补 `svc.themeTouched = true;`（或更好：把 `theme` 的赋值收进一个 `setTheme(n)` 方法，内部统一置 `touched` 并重置轮播计时）。

  或让 `loadPrefs()` 在 `service` 就绪后再应用一次偏好（引入一个 `applyPrefsOnce()`）。
- `Logger.i` 改用 `Index.themeName(this.theme)`。
