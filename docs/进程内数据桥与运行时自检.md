# 进程内数据桥 + 运行时自检（2026-10-15）

## 一句话

数据桥从**外部 node 脚本**改成了 **DSH 插件**（进程内），随 DSH 启动自动推遥测；
App 侧加了**运行时体检**（链路层），和原有的协议 KAT 自检互补。

---

## 一、为什么原来是外部的，以及为什么能改成进程内

### 原来的形态
```
DSH 会话文件(zstd) ──▶ [外部 node 脚本 dsh-bridge.mjs] ──UDP──▶ 屏幕 App
                              ↑
                     要手动 ./start.sh，还要 zstd.exe
```
痛点（用户原话）：**"数据桥的功能实现并到软件本身，而不是需要接触外部提供"** ——
要手动起进程、要额外的二进制、忘了起就没数据。

### 改造成进程内的**关键前提**（本次实测确认）
| 问题 | 结论 |
|---|---|
| 会话文件是 zstd 压缩的，ArkTS 有 zstd 吗？ | ❌ `@ohos.zlib` 只有 `DEFLATED`(zlib)，**没有 zstd** |
| 那 App 内解压这条路通吗？ | 系统有 `/system/lib64/libzstd.z.so`，但**普通应用加载系统库受限**，且无法在本机验证 → 风险高 |
| 有没有**不需要解压**的明文来源？ | ❌ `cost-meter/ledger.json` 和 `session_projcache.json` 都**停在 10-13**（过期 2 天），当不了实时源 |
| **那怎么办？** | ★ **DSH 的 node 原生带 zstd**：`node:zlib` 里有 `ZstdDecompress` / `zstdDecompressSync`（实测 Node 26）。多帧 `session.v4.jsonl.zstd` 一次就能解开（13.7MB → 45MB / 313ms） |

→ 结论：**把桥做成 DSH 插件**。插件跑在 DSH 进程里，能直接读解压后的会话，
   不需要 spawn 任何进程、不需要外部二进制。这才是真正的"in-process"。

---

## 二、插件实现（`dsh-plugin/dsh-lcd-bridge/`）

| 文件 | 职责 |
|---|---|
| `package.json` | `dsh.bundle.patch` 指向 `cordis.patch.yml`（DSH 的插件声明格式） |
| `cordis.patch.yml` | `- insert: [{id, name}]` 注册项 |
| `session.mjs` | 找当前会话 / 解压 / 提炼状态 |
| `index.mjs` | 本机采集 + UDP 推送 + 生命周期 |
| `../setup.sh` | 一键安装（复制到 profile + 注册 + YAML 校验 + 状态自检） |

### 会话读取：两层节奏（实测调出来的）

| | 覆盖率 | 耗时 | 拿到的字段 |
|---|---|---|---|
| **尾部快读**（8MB 尾部 + 最早帧起点） | 最近 ~6000 行 | 几十~几百 ms | state / activity / tool / turn / step / contextUsed / todos |
| **全量流式解码**（`createZstdDecompress`） | 全部 18000+ 行 | ~1.5–2.4 s | + model / provider / contextWindow / title / **当日用量** |

因为全量要 2 秒级、不能每秒跑，所以：**快字段每秒刷，重字段每 30 秒刷一次，然后合并**
（`HEAVY_KEYS`）。

### 踩过的坑（都修了，记在这里免得重犯）

1. **尾读只解出 2 行** —— 一开始"从最后一个帧头解压"，而多帧流最后那个帧可能只有几百字节。
   改成**取尾部范围内最早的帧起点**。
2. **从文件头读元数据全部失败**（32KB→8MB 都报 `unexpected end of file`）——
   整个会话是**一个持续写入的大帧**，尾部不完整就解不开。
   所以必须**流式解码器**（喂完整文件、让未完成的尾部自然丢弃）。
3. **`readAllLines` 第一版解出 0 行** —— zlib 的流是**异步**产出数据的，
   同步 `dec.write()` 后立刻 `dec.read()` 什么也拿不到。必须 `for await`。
4. **model/provider 一开始是空的** —— 它们在 `request/context` 的 **`data` 这一层**
   （`{provider, model, contextWindow}`），而且这行在**文件很前面**，尾部窗口覆盖不到
   → 只能靠全量刷新。
5. **前几包 model 为空** —— 全量解码要 2.4 秒，而推送从第 1 秒就开始了。
   加**启动预热**：先 `await` 一次全量再开始推。

## 三、运行时自检（`entry/src/main/ets/service/RuntimeCheck.ets`）

### 与协议 KAT 的分工

| | 查什么 | 何时能发现 |
|---|---|---|
| `usb/SelfTest.ets`（已有） | **代码对不对**：握手包字节 / 分块流哈希 / JPEG 上限 / 端点挑选。期望值由独立的 `tools/ly_reference.py` 算出 | 纯计算，开机就能跑，**不需要屏幕** |

### 检查项（6 项）
```
协议自检(KAT)      ← 把已有结果并进体检表
USB 屏幕连接       usbOpen + 设备串
推帧到屏幕         sent>0；errors 只作参考（偶尔一次不算故障）
数据桥遥测         优先看 age（≤15s 算在推），其次看累计包数；从未收到会明确指出
画面源(VM 抓帧)    没配 VM 也算正常（只要不是一直在错）
本机数据采集       HostStats 的 CPU / 内存
```
界面位置：**设备卡 → `运行时体检` 一行**（`全部通过（6/6）` 或 `5/6 通过｜待查：数据桥遥测`）。

同时把原来那句"数据桥: cd ~/WorkBuddy/TrofeoLCD/bridge && ./start.sh"的提示改掉了
—— 现在不再需要手动启动外部脚本：
```

```

### ★ 为什么不能"复制文件 + 手写 cordis.patch.yml"

我第一版就是这么做的，DSH 启动时**直接预检阻断**：

```
[阻断] dsh-lcd-bridge@? — bundles 里引用了但没装
    建议：dsh plugin --profile web add dsh-lcd-bridge
```

原因：DSH 的 profile 有**两处**声明，缺一不可 ——
| 位置 | 含义 |
|---|---|
| `package.json` 的 `dependencies` | 这个包**装进来了** |
| `package.json` 的 `dsh.profile.bundles` | 这个包**要被加载** |

只塞 `node_modules/` 两处都不满足 → 被阻断。
正确做法是走 DSH 自己的命令（底层就是 pnpm）：

```bash
dsh-harmonyos -- plugin --profile web add file:/path/to/dsh-plugin/dsh-lcd-bridge
```
它会把 `file:` 依赖写进 `dependencies`、装进 `node_modules`、**并自动把包名加进 `bundles`**。
`setup.sh` 已经改成走这条路，是**幂等**的（重跑显示 `Already up to date`）。

### 验证插件真的被加载（三种手段，按可靠性排序）

1. **直接调 `apply()`**（最硬）——用假 `ctx` 导入插件模块并调用，看它是否打启动日志：
   ```
   导出: apply, inject, name
   name = dsh-lcd-bridge | inject = []
   [dsh-lcd-bridge] 已启动：127.0.0.1:54545 每 1000ms 推一次（进程内，无外部依赖）
   ```
2. **UDP 抓包**（换端口跑插件，实测抓到 11 包）：
   ```
   model=deepseek-flash provider=deepseek-official
   state=busy/执行命令 tool=bash turn=148 step=133 proj=WorkBuddy
   今日token=3622201 上下文=363349/1000000
   本机 CPU=46.3% 内存=18821/23859MB 14核  todos=8  source=dsh-plugin
   ```
3. 起独立实例看启动日志有没有 `[阻断]`（注意：并存的实例会因抢 task-board 锁而少激活一项，**那是既有现象，与本插件无关**）

### 与原来外部桥的关系
两者**载荷同构**，可以共存（App 只认最新到达的包）。建议二选一：
插件跑起来之后就不用再 `bridge/start.sh` 了。
`bridge/` 目录先保留（Windows 版还在用外部桥那套）。

## 六、还没做的

1. **重启 DSH 后的真机验证** —— 需要重启 DSH 让插件加载（会打断当前 GUI 会话，所以留给用户决定时机）。

   现在桥随 DSH 走，所以这个脚本的语义变成"确保插件已装 + 装 App 到设备"；
   计划用 `hdc install` 走一遍，下一轮补。
3. **本机采集的数据源统一** —— App 侧 `HostStats`（走 hidebug/batteryInfo）与
   插件侧的 `os.cpus()/os.totalmem()` 是两套。目前插件的 system 会覆盖 App 的本地采集，

   现在靠 App 侧原有的余额逻辑。若要内建，需要 API key 与定时刷新。

# 补充：性能调优（2026-10-15 第2轮，实测数据）

## 问题：第一版会把 DSH 拖卡

插件与 DSH **同一个进程** —— 插件阻塞事件循环就是 **DSH 卡顿**。第一版实测：

| 操作 | 耗时 | 频率 | 占用 |
|---|---|---|---|
| 尾部快读（**8MB** 尾部 + 提炼 6000 行） | **380 ms** | 每秒 | **38%** |
| 全量流式解码 | 1300 ms | 每 30s | 4.4% |
| 事件循环最大阻塞 | **612 ms** | — | — |

38% 的占用 + 每秒 380ms 的停顿，会把 DSH 明显拖卡。

## 调优依据：尾部大小 vs 耗时（13.6MB 会话实测）

| 尾部 | 解压 | 行数 | 提炼 | state/turn/step |
|---|---|---|---|---|
| 0.5MB | 11ms | 652 | 21ms | busy/149/3 |
| **1MB** | **25ms** | 1302 | **47ms** | busy/149/3 |
| 2MB | 45ms | 2461 | 65ms | busy/149/3 |
| 4MB | 77ms | 5238 | 114ms | busy/149/3 |
| 8MB | 160ms | 10804 | 267ms | busy/149/3 |

★ **关键发现：活字段（state/activity/tool/turn/step）在 0.5MB 就已经正确**，
8MB 纯属浪费。所以快路径压到 **1MB**。

> 注：`todayUsage`（当日用量）无论多大尾部都不完整 —— 它需要覆盖当天**全部**行，
> 本来就该由低频全量刷新提供，快路径那个值会被覆盖。

## 调优结果

| 项 | 改前 | 改后 |
|---|---|---|
| 快路径 | 380 ms/s（38%） | **78 ms/s（7.8%）** |
| 全量刷新 | 每 30s | **每 60s**（这些值变化慢） |
| 合计 CPU | ≈42% | **≈10%** |

## 边界健壮性（13 项测试全通过）

插件与宿主同进程，**任何未捕获异常都会影响 DSH**，所以专门测了异常输入：

```
① findCurrentSession   不存在目录 ✅ / 空目录 ✅
② readTailLines        文件不存在 ✅ / size=0 ✅ / 垃圾内容（非 zstd）✅
③ deriveState          空数组 ✅ / 坏 JSON ✅ / 半截行 ✅ / data:null ✅
                       / 缺 data ✅ / usage 坏类型 ✅ / todos 坏类型 ✅
④ apply()              缺 logger 的 ctx ✅（可选链生效）
```

另外给**预热的异步块加了双层保护**（内层 try/catch + 外层 `.catch()`），
确保启动阶段任何异常都不会冒泡到宿主。

## 安装方式的两个坑（都修进 setup.sh 了）

1. **pnpm 对 `file:` 依赖会"Ignore 文件变化"** —— 改了源码重装，
   profile 里还是**旧版本**（实测：`TAIL_BYTES` 仍是 8MB）。
   修法：**先 `rm -rf node_modules/<包名>` 再 add**，才会真正拷新的。
2. **`verify` 的注册判据要看两处** —— 早期查的是 `cordis.patch.yml` 里的手工注册行，
   而正规安装根本不写 patch，于是误报"未注册"。
   现在查 `dependencies` + `dsh.profile.bundles` 两处。

## `run-app.sh` 的一个 shell 坑

`python3 - <<'PY'` 这种 heredoc **会把 stdin 占成"脚本内容"**，
于是 `printf '%s' "$data" | python3 -` 的管道数据**进不去** ——
表现是"手动跑能解析、脚本里恒报 `/diag` 不是合法 JSON"。
修法：**用命令行参数传数据**（`python3 - "$data" <<'PY'` → `sys.argv[1]`）。

另外：`pkill -f '某模式'` 会**匹配到执行它的 shell 自身**
（因为模式出现在那个 shell 的命令行里）→ 把自己杀掉（实测遇到 SIGTERM）。
要按模式清理进程时改用别的方式。

# 补充：修掉一个影响面很大的陈年 bug（2026-10-15 第3轮）

## 现象

体检日志说"0s 前收到｜累计 2038 包"，而**同一时刻** `/diag` 报 `bridgeAgeSec: -1` —— 两个读数互相矛盾。

## 根因：`FrameStats.bridgeAge` 从来没人赋值

```ts
// Dashboard.ets:23
bridgeAge: number = -1;      // ← 初值 -1，全仓**没有任何地方写过它**
```

它被 **7 处**读取，于是这些地方**永远拿到 -1**：

| 读取处 | 表现 |
|---|---|
| `Dashboard.ets:424` | 仪表盘右上的「桥 **○**」永远不亮 |
| `ThemeDiag.ets:196-203` | 「数据桥 **无数据**」，且状态判据恒为假 |
| `ThemeWall.ets:59-65` | 「桥 **○**」恒橙 |
| `ThemeMac.ets:127` | 恒显示 `--` |
| `ThemePages.ets:97` | 桥状态恒为不健康 |
| `Index.ets:564-567` | 界面「数据桥」一行恒显示"无数据" |
| `LcdService.ets:1416,1495` | `/diag` 的 `bridgeAgeSec` 恒 -1 |

→ **遥测明明在推，屏幕 5 个主题上的桥指示灯却全都不亮**，界面上也显示无数据。
而 `/diag` 那个恒 -1 更坑：**排障时会直接把人带偏**（我前两轮就一直拿它当判据，
还因此错误地判断过"遥测没通"）。

## 修法

在帧循环更新 stats 的地方（与 `usbOpen` 等同一处）接上真实状态：

```ts
this.stats.usbOpen = this.usb.isOpen;
// 数据桥新鲜度
const bsLive = this.bridge.state;
this.stats.bridgeAge = bsLive.lastRxTs > 0 ? bsLive.ageSec() : -1;
```

## 验证

| 时刻 | `/diag` 的 bridgeAgeSec |
|---|---|
| 修前（遥测在推） | **-1**（恒定，与实际无关） |
| 修后（基线） | `0` |
| 修后（插件推送中） | `0`（跟随真实秒数） |

体检表同时报 `全部通过（6/6）`、`0s 前收到｜累计 52 包`。

## 教训

**一个字段被读取 7 次、却从没人赋值** —— 这种 bug 不会崩、不会报错，
只会让所有相关 UI 静默显示成"默认值"，看起来像"功能没做"。
`RuntimeCheck`（本轮的 C 项）正是靠"两个读数互相矛盾"才把它暴露出来的：
体检日志与 `/diag` 用的是**两条不同的取数路径**，对不上就说明有一边是坏的。

| **`LcdService.bgUrl`** | ⚠️ **真死字段，但属"未接线的功能"** |

## 关于 `LcdService.bgUrl`

```ts
bgUrl: string = '';                       // 全仓无人赋值
// fetchBgImage()（在 tick 里真的被调用）:
if (this.bgPm !== null || this.bgUrl.length === 0) { return; }   // ← 恒为真，提前返回
const resp = await req.request(this.bgUrl, {...});              // ← 永远执行不到
```

也就是说「从 HTTP 拉一张背景图」这条路径**整段是死的**：

- 桥侧**是实现了的**：`dsh-bridge.mjs --bg <文件>` 会在 `127.0.0.1:54547` 起一个
  图片服务（`BG_PATH` / `BG_PORT`，实测代码在 1072~1089 行）。
- App 侧也**留了接收代码**（`fetchBgImage` + `bgPm` + 定时调用）。
- **缺的是接线**：载荷里**没有** `bg` 字段，所以 App 无从知道该请求哪个地址。

→ 接上它需要**两端都改**（桥在载荷里带上地址、App 读取并写进 `bgUrl`），
  属**新功能**而非修 bug，因此本轮**未做**。想要的话可以单独提。
  （另外 App 已有可用的图片背景方案：`rawfile/bg_sample.jpg` → `Backdrop.image`。）

## 扫描脚本的价值

这个"有读取无赋值"的检查值得固化成常规检查 —— 它抓到的那种 bug
（UI 恒显默认值、排障读数恒为 -1）**不会在编译期或运行期报任何错**。

# ★ 最小化停推问题：排查记录与两处修复（2026-10-16）

## 用户报告
"点最小化就立刻停止推送"；HOME 键切后台则正常。

## 实测：两者确实是不同路径

| 操作 | `bgCount` | 结果 |
|---|---|---|
| **HOME 键**（`uinput -K -d 1 -u 1`） | **不变**（一直 0） | ✅ 连续 240 秒正常推（sent 19067→19550，2.4 fps） |
| **点最小化** | **7→8** | ❌ **约 300ms 内整个 JS 事件循环被冻结** |

冻结的证据（13:26 那次，45 次探测 × 90 秒**全部失败**）：
```
13:26:09  tick=151141  sent=41920  usb=True  bg=8 fg=8   ← 最后一条读数
13:26:12  /diag 完全读不到（此后 90 秒全失败）
```
- `tickCount` **停止增长** ⇒ `setTimeout` 不再回调
- HTTP（`/diag`）也不响应 ⇒ **不是推送失败，是 JS 线程整体冻结**

## 排除了两个猜测（都有数据支撑）

| 猜测 | 实测结论 |
|---|---|
| 保活被系统拒 | ❌ **推翻** —— 新增诊断显示 `bgMode='dataTransfer'`、`bgErr=''`，申请**成功**了 |
| 一进后台就停 | ❌ **推翻** —— HOME 切后台连续 240 秒正常 |

## 从 SDK 文档挖到的关键规则

`@ohos.resourceschedule.backgroundTaskManager.d.ts`：
```
DATA_TRANSFER = 1
"若数据传输速率低，超过 10 分钟的 DATA_TRANSFER 持续任务会被取消"
SYSTEM_SUSPEND_DATA_TRANSFER_LOW_SPEED = 4
```
而本应用**内容签名未变就跳帧**，屏上静止时 3 秒才推一帧 → 速率极低 → 容易命中这条。

## 两处修复（已实现并编译通过）

### ① 后台期间关闭跳帧（**治本方向**）
`onBackground` 实测会触发，所以用它当开关：
```ts
// LcdService
private backgrounded: boolean = false;
setBackgrounded(v: boolean): void { ... }
// 跳帧判断加短路
if (!this.backgrounded && sig === this.lastSig && ...) { 跳过 }
```
后台时**持续推帧**，把传输速率维持住，避免被判定为"低速传输"而挂起。

### ② 回前台立刻补一帧（**兜底**）
```ts
// EntryAbility
onForeground(): void {
  LcdService.active?.setBackgrounded(false);   // 恢复跳帧 + 内部调 forceRefresh
}
```
`forceRefresh()` 清掉 `lastSig`/`pendingSig`/`lastPushMs` 并立刻 `tick()`，
把"恢复后最多 3 秒空窗"压到毫秒级。

### 为定位问题新增的诊断（接进 `/diag`，不依赖 hdc）
```
bgMode  申请成功的后台模式名（空 = 全部被拒）
bgErr   失败原因（含错误码）
tickCount  帧循环回调次数（不再涨 ⇒ 事件循环被冻结）
bgCount / fgCount  onBackground / onForeground 调用次数
```

## 仪表本身的两个坑（我踩过）
1. **计数器插错位置**：`tickCount++` 一开始插在 `setTimeout(tick, 50)` 之前 ——
   那是**启动路径**才走的分支，导致 `tickCount` 恒为 1，看着像"循环死了"。
   正确位置是 `tick()` 方法**最开头**。
2. **`python3` 有时不在 PATH**：这台机器上要用
   `/storage/Users/currentUser/.harmonybrew/bin/python3`，
   脚本里 `command -v python3` 会失败且静默跳过改动。

## 待验证（阻塞项）
验证 ① 需要**真屏在手**：`sent` 与 `skip` 的变化只有在 USB 屏连着时才有意义
（屏没接时 `usbOpen=False`、`sent=0` 是**正常现象**，不是故障）。
另外 `aa start` 在设备锁屏/受限时会被拒，必须手动点图标启动。

# ★ 熄屏停推：运行锁（2026-10-16 第2轮）

## 用户报告
"现在最小化不会了，熄屏还是会，能保持吗？"
—— 即**最小化已修好**，但**设备熄屏后仍停推**。

## 排查与实现

`continuous task`（dataTransfer）挡不住熄屏这一种。SDK 里另有**运行锁**：
`@ohos.runningLock`，权限 `ohos.permission.RUNNING_LOCK`
（查 `PermissionDefinitions.json`：`system_grant` + `availableLevel=normal`
→ 安装即授予，普通应用可申请）。

### 锁类型选择（照 `acquireBgTask` 的多模式策略）
| 类型 | 说明 | 状态 |
|---|---|---|
| `BACKGROUND = 1` | 熄屏时防休眠 | ⚠️ **API 10 起废弃** |
| `BACKGROUND_USER_IDLE = 129` | 用户空闲时防自动休眠 | ✅ 较新 |
| `PROXIMITY_SCREEN_CONTROL = 2` | 接近传感器控屏 | 不适用，留兜底 |

`isSupported()` 先探测再按优先级尝试，谁成用谁 —— **不猜哪个可用**。
成功与否全部接进 `/diag`：`lockHeld` / `lockType` / `lockErr` / `lockSupport`。

### `hold(-1)`
文档：`-1` = **永久持有**（The lock is permanently held）。传 0 或正数会
计时结束后自动释放，不适合"长期喂屏"。

### 为什么锁在启动时拿、一直持有
熄屏不一定走 `onBackground`，放在那里加锁会漏。状态副屏的语义就是
"只要应用在跑就一直喂屏"，所以启动即持有、直到应用真正退出。

## 我引入并修掉的一个严重问题（值得记下来）

改 `/diag` 时，我的字符串替换**落在了一行长模板字符串的中间**，
并且把原来的收尾反引号吃掉了：

```ts
// 坏：缺收尾 ` → 模板串跨行 → 字符串状态错乱
+ `,"usbClaimBlocked":${jsonBool(this.usb.claimBlocked)}
// 好：
+ `,"usbClaimBlocked":${jsonBool(this.usb.claimBlocked)}`
```

后果：整个文件**括号平衡变成 +2**（545/543），类被提前关闭，
后面的方法全掉到类外 → 编译器报一堆莫名其妙的
"Property 'active' does not exist on type 'typeof LcdService'"。

**定位手法（这次很有效，值得复用）**：
1. 用 `node` 做逐字符扫描（能正确处理字符串/模板串/注释）算出真实 depth
2. 用**方法名清单**比对当前文件与备份 → 找到第一个名字对不上的方法

# ★ Dotii 轮播不翻页：内容签名漏项（2026-10-16 第3轮）

## 用户报告
"dotii 轮播的标怎么都不变的？" —— Dotii 的页/指示点在屏上**永远停在第一页**。

## 根因：内容签名漏掉了"打印机格里的 Dotii 页号"

`contentSignature()` 原来只这样计 Dotii 的页与表情：
```ts
${this.theme === 5 ? this.dotiiState.page : 0}
${this.theme === 5 ? this.dotiiState.expr : 0}
```
而用户的配置是 **主题 0 + `printerCell='v6'`** —— Dotii 画在**打印机格**里
（`ThemeDotiiCell.render`），**主题不是 5** → 页号**不进签名**。

于是每 10 秒 `prepareDotiiState()` 推进 `ds.page` 时：
```
ds.page 0→1，但签名不变 → 被"内容未变则跳过"挡掉 → 不重推 → 屏上停在第 0 页
```

**这与代码里已记录过的另一处同类 bug 完全同型**（`printerSlot` 的注释里写过：
"子页从 2→3、3→0 时内容签名不变 → 该帧被跳过 → 打印机格周期性停住 20 秒"）。
说明"**任何时间驱动的显示状态都必须进签名**"这条规则当时没有系统性地落实。

## 修法
抽出与渲染侧**同一判定**的辅助函数（单一真源），签名与渲染共用：
```ts
private dotiiShownInCell(): boolean {
  return this.theme === 0
    && (this.printerCell === 'dotii' || this.printerCell === 'v4'
      || this.printerCell === 'v6');
}
// 签名：
${(this.theme === 5 || this.dotiiShownInCell()) ? this.dotiiState.page : 0}
${(this.theme === 5 || this.dotiiShownInCell()) ? this.dotiiState.expr : 0}
```

## 新增可验证读数（`/diag`）
```
dotiiPage    当前页号（0..3）—— 应在 10 秒内递增
dotiiExpr    当前表情（0..7）
dotiiInCell  Dotii 是否正画在打印机格里（= 签名是否该计页号）
```
**验证方法**：主题 0 + printerCell=v6 时，`dotiiPage` 应每 10 秒 +1。

## 顺带发现（另一处，待确认）
`printerPanel` 里**只实现了 `sub === 0`（概览）与 `sub === 1`（温度）两个分支**，
而 `printerSlot()` 返回 0..3、底部指示点画 **6 个**（`PRINTER_SLOTS = 6`）：
- 槽 2（AMS）、槽 3（表情）**无渲染分支** → 那 20 秒格子是空的
- 指示点用 `i === sub` 点亮，sub 最大 3 → **后两个点永远不亮**

这与 `PRINTER_SLOTS = 6` 的注释（"3/4 = 表情、5 = 打砖块"）**不符**。
注释里也写了"槽 3/4/5 的渲染在 B 线里实现"（交接单 HANDOFF-打印机格复刻.md），
所以可能是**已知的未完成项**，需要对照交接单确认再动手。

## 先纠正我自己的误判

| 2 | 进程 CPU | 冻结后 12 秒内 `ps` 的 CPU 时间**一个时钟都不走**（`00:09:18` 不变） |
| 3 | App 日志 | 停在那一刻，之后完全无输出；`/diag` 连续 6 次无响应 |

**两个保活机制在冻结时都还持有**，系统照样冻：
```

lockHeld  = True                lockType = 'BACKGROUND'   lockErr = ''
```

## 触发条件（实测，非常明确）

| 操作 | `onBackground` | 结果 |
|---|---|---|
| **HOME 键** | **不触发** | ✅ 连续 3 分钟正常（`tick 6059→6372`、`sent 4265→4470`） |
| **窗口最小化** | **触发** | ❌ 约 10~18 秒后被 cgroup 冻结 |

→ **系统只在"窗口被最小化"这条路径上冻结应用**，与数据传输速率无关
（冻结时 USB 插着、`sent` 一直在涨）。

**结论：这是平台行为，不是本应用代码的 bug，应用侧的保活声明挡不住。**

`@since 14`，本机 API 26 可用。`/diag` 新增读数 `titleBtn` 验证结果：

```

"最小化"对它没有意义、且是**唯一**会触发冻结的操作；而用户仍可用
**HOME 键 / 切到别的应用**离开（那条路径实测不冻）。保留最大化与关闭按钮。

**完全可逆**：把第二个参数改回 `true` 即恢复。

# ★ 审计遗留三项修复（2026-10-19 收尾）

## M12 · 打砖块只有 0.24× 速（用户可见）

**成因（两层叠加）**
1. `pongAdvance` 有 `need = min(floor(dt/20ms), 8)` 上限 → 每帧最多补 160ms 游戏时间
2. 空闲档帧间隔 `INTERVAL_IDLE = 500ms`（且每帧渲染+编码+USB ≈160ms）→ 实际周期 ~660ms
   ⇒ 160/660 ≈ **0.24×**，屏上是明显慢动作

**只放开上限会更难看**（500ms 一帧补 25 步 → 球每帧瞬移），所以两件事一起改：

| 改动 | 内容 |
|---|---|
| 帧率 | 新增 `syncPongInterval()`：主题 4 或「打印机格槽 5」可见时把 `forceIntervalMs` 压到 **66ms（≈15fps）**，离开即恢复。复用序列播放那套 save/restore，不覆盖 `/set?fps` |
| 物理 | `need` 上限 8 → **32**，并把 `dt` 钳到 640ms（防长时间停顿后一次补上千步） |

**实测验证**（`/diag` 新增 `cellPongTick`）：
```
21:19:33  slot=5 cellPongTick=151
21:19:39  slot=5 cellPongTick=455    Δ=304 / 6s = 50.7 tick/s
```
目标速率是 50/s（`kTickMs=20ms`）→ **1.0× 正确速度** ✅
（`forceIntervalMs` 也验证：进槽 5 变 66，离槽回 0）

> 注：`fps` 指标仍显示 ~2.9 —— 因为**每帧成本本身约 160ms**（渲染+编码+90KB USB 推送），
> 这是硬件/协议上限，不是 bug。物理速度已按真实时间推进，不受帧率影响。

## U1 · `open()` 无并发保护 → pipe 泄漏

原来唯一保护是 `opened`，而它要**握手成功后**才置位；中间有 `ensureRight`（权限弹窗可数秒）、
`connectDevice`、`claimInterface`、`handshake` 多个 await 点，调用侧有 5 处互不互斥的调用。
并发进来各自 `connectDevice` → 后一个覆盖 `this.pipe` → 前一个 pipe 永不 `closePipe`、
接口永不 `release` —— 正是"反复失败后再也连不上、只能拔插"的成因。

**修法**：`opening: Promise` 单点复用，原 `open()` 体抽成 `doOpen()`。

## U7 · `close()` 不等在途传输 → 撕流

分批发写一次会同时挂多个 `bulkTransfer`，此时 `closePipe` 会把分块流撕开 → 花屏/停更。

**修法**：
- `pendingWrites` 计数：每批发写前 `+= 本批数量`，`finally` 里逐条 `noteWriteDone()`
- `close()` 若发现 `pendingWrites > 0` → 置 `closeDeferred` 并**延后**，归零后自动真正释放
- 写入前检查 `closing`，关闭中直接放弃本帧（下一轮重连）

### 环形彩条的两个后续修正（用户反馈驱动）

**① 四角"细线交叉"**
原因：内沿/外沿的虹色细线各用 4 条 `fillRect` 横贯整宽/整高，在四角必然十字交叉。
修法：**直接去掉那 8 条细线**，只保留深色底带（底带也改成"上下满宽 + 左右只补中间"，角上不叠两遍）。

**② 文字"没有拐弯，穿过去了"—— 这是路径几何算错了**
旧实现把四条边当成：
- 上边 `y=mid, x∈[0,W]`（一直画到屏幕最右边缘）
- 右边 `x=W-mid, y∈[0,H]`（从屏幕最顶开始）

两者在角上**并不相接**：上边终点是 `(W, mid)`，右边起点是 `(W-mid, 0)`，
相差 `(mid, -mid)`（约 17,17px ≈ 一个字宽）→ 视觉上就是字"跳"过去、没有拐弯。

修法：改走**环带中心线**的闭合矩形：
```
m = band/2
上边 (m,m) → (W-m,m)        长度 W-band
右边 (W-m,m) → (W-m,H-m)    长度 H-band
下边 (W-m,H-m) → (m,H-m)    长度 W-band
左边 (m,H-m) → (m,m)        长度 H-band
P = 2(W-band) + 2(H-band)
```
这样四段在角上首尾相接，字到角上正好转 90°，是真正的"绕着走"。

**③ 两种排布模式（`/set?ringmode=`）**
| 值 | 行为 |
|---|---|
| `1`（默认） | **连续不断档**：文本重复铺满整圈，始终有字 |
| `0` | **单份跑完整圈再重复**：只有一份，跑出终点后重新进入，中途环上会空一段 |

### 彩虹条相位调参结论（2026-10-20 定稿）

**问题**：用户反馈"只是闪，不是滚动"。

**根因**：屏幕实测只有 ~3–3.5fps（每帧 ≈300ms，瓶颈是 JPEG 编码 + USB 推送）。
原先用**连续速度** `0.30 度/ms` → 每帧前进 90°，而一个彩虹周期才 360°
→ 相邻两帧颜色换掉 1/4 个彩虹（≈530px），眼睛读成"闪"而不是"流"。

**修法**：相位改成**按帧率对齐的定步长**
```
steps  = floor(nowMs / 300)
phase  = (steps × ringStepDeg) % 360
```
`ringStepDeg` 默认 **24°**，可用 `/set?ringdeg=N`（4..120）调。

**实测定档**：

| ringdeg | 每步位移 | 绕一圈 | 视觉速度 | 评价 |
|---|---|---|---|---|
| 8 | 51px | 27.0s | 171px/s | 很顺但偏慢 |
| 12 | 77px | 18.0s | 257px/s | 顺 |
| **24** | **154px** | **9.0s** | **514px/s** | **用户选定：最像"滚动"** |
| 28 | 180px | 7.7s | 600px/s | 偏快，开始像闪 |
| 36+ | 225px+ | <6s | >750px/s | 明显闪 |

**注意**：`ringdeg` 是内存态，App 重启会回到默认 24（正好是用户想要的默认）。

**本质限制**：3.5fps 下任何滚动都只能是"跳跃式前进"，只能把跳幅调小到不刺眼。
提升帧率需要降分辨率/降质量，此前实测收益仅 +13%（`q=0.95→0.6`），不值得。

### 新增：彩虹条「呼吸」效果（2026-10-20，用户提议）

用户判断很准：**低帧率下"滚动"必然像闪，但"呼吸"可以很顺** —— 因为呼吸是慢周期（3.6s），
3.5fps 下每个周期有 ~12 帧采样，足够读出平滑明暗；而滚动每帧要跳一大段。

**实现**：
- 彩虹色相**静止**（只按弧长定位，几乎不动：叠加 0.006°/ms 的极慢漂移，避免太死板）
- 整体亮度做余弦呼吸：`breath = 0.5 - 0.5·cos(2π·t/T)`，亮度 `v = 0.40 + 0.60·breath`（40% ↔ 100%）
- `hsvToCss(hue, value)` 增加亮度参数

**关键配套修改（不做就会失效）**：
内容签名里整点彩条那项原来是 `Math.floor(Date.now()/1000)`（**1 秒粒度**），
会把呼吸的中间帧当成"内容未变"跳过 → 呼吸变成每秒跳一档。
改成 **250ms 粒度**（与当前帧间隔 ≈300ms 对齐）后每帧都重推。

**实测**（`/diag` 新增 `ringBreath` 0..100）：
```
01:17:31 breath=13
01:17:32 breath=55
01:17:33 breath=97   ← 峰
01:17:34 breath=3    ← 谷
01:17:36 breath=93
01:17:38 breath=1
01:17:39 breath=79
```
干净的 3.6 秒正弦，峰谷都到位；抓帧对比：`breath=99` 全饱和鲜艳，`breath=8` 明显压暗到约 40%。

**参数**：
| 参数 | 说明 |
|---|---|
| `/set?ringfx=breath` / `scroll` | 呼吸（默认）/ 滚动 |
| `/set?ringbreath=N` | 呼吸周期 ms（800..20000，**默认 5800** ← 用户 2026-10-20 定） |
| `/set?ringband=N` | 带宽（默认 34） |

**最终默认值**：呼吸周期 **5800ms**（5.8 秒一呼一吸），已写进 `Overlay.ringBreathMs` 的初值，
App 重启后保持。实测峰→峰 ≈5.9s、谷→谷 ≈5.0s（采样含抖动），与 5800ms 一致。

## 三个必须解决的坑（都是实测撞出来的）

**① 4fps 下"一帧跨 4 格"，自动驾驶来不及判断**
屏幕 ~4fps，一帧要覆盖 0.25 秒。若整块 0.25s 一次 `update()`，玛丽一帧就跨过 4 个格子，
实测**一直掉进坑里**。改成**内部按 1/60 秒分步推进**（画面仍每帧只推一次，帧率不变），
物理与决策都变成 60Hz 精度。

**② 只按一个子步就松手 = 没跳**
游戏有 `JUMP_CUT`（松手砍掉上升速度）。原来每帧只 `virtualDown(JUMP)` 一个子步就松，
等于"原地小跳"，实测**卡在水管前反复跳不过去**。改成**整帧按住**（≈0.25s）＝满高度跳跃。

**③ 需要"前方危险"探测**
光靠定时跳会乱跳掉坑。给 Game 加了 `dangerAhead()`（移植版新增，公开方法）：
① 前方 44px 脚下没有实心方块 → 坑；② 身体高度处实心 → 墙/水管；
③ 前方 72px 内有板栗仔。自动驾驶只在 `dangerAhead()` 为真（或卡住 >1.2s）时才跳。

## 效果（实测）

第一次修（分步+探测）：x 到 1574 后卡死（小跳跳不过水管）
全部修完：x 持续推进到 ~4000，14 次采样（56 秒）零死亡
```

### 修「被水管卡住」—— 找到并修掉一个真 bug（2026-10-21）

用户反馈：**会被水管卡住**。这次没有继续调参数，而是**把地形打出来**定位：

给 Game 加了 `terrainInfo()`，打印玩家周围 3×5 的 tile id。卡住时的读数：
```
x=870  r10: 0 0 6 7 0 | r11: 0 0 8 9 0 | r12: 0 0 8 9 0 | r13: 1 1 1 1 1
```
`6/7/8/9` = `PIPE_TL/TR/L/R` → 是一根 **3 格高（48px）的水管**，玩家就贴在它左面。

按物理算：`JUMP_VEL=720, GRAVITY=2400` → 最大跳高 `720²/(2×2400)` ≈ **108px ≈ 6.75 格**，
跳 48px 的水管理论上绰绰有余。所以不是跳不上去，是**跳的时候被砍了**。

**根因（真 bug）**：`MarioDemo.step()` 每帧开头都执行 `this.jumpStepsLeft = 0`，
而一帧只有约 15 个子步（0.25s），满高度跳需要按住 **0.37s**（到顶点要 0.3s）。
每帧清零 → 实际最多只按住 0.25s → 松手触发 **JUMP_CUT** → 高度被砍掉一截
→ **越过管顶的时间不够往前挪** → 贴着管子反复跳，看起来就是"被卡住"。

修法：**去掉每帧重置**，让 `jumpStepsLeft` 自然递减到 0，按键状态可以跨帧延续。
另外把 `JUMP_STEPS_FULL` 从 15 提到 **22**（0.37s > 0.3s 上升时间），确保全程不 cut。

**配套的两道保险**（都只在演示模式生效）：
| 机制 | 作用 |
|---|---|
| 卡住 1.5s → **小幅前推 24px + 抬高 6px + 轻抬 vy** | 少数"台阶贴水管/头顶有砖"的位置物理上过不去，前推在 3× 放大下几乎看不出 |
| 卡住 8s → 换关 | 兜底，绝不让画面停在原地 |

**修复前后实测（各 100 秒）**：
```
修复前：x=870 水管处反复停留，每处停 8~10 秒；关卡靠"卡住换关"推进
修复后：无任何长时间同位置停留（每次采样 x 都变了）
        关卡 0→1→2→3→4→5 自然推进；score 1300→8300；coins 4→19
```

### 修「选二次元主题时电脑端界面卡、不跟手」（2026-10-21）

用户反馈：选主题 10（赛博二次元）/11（二次元壁纸）时，**电脑上的应用界面**卡顿不跟手
（不是副屏问题）。

#### 先量化

`/diag` 的 HTTP 处理与帧循环跑在**同一个 JS 线程（UI 线程）**上，所以它的往返延迟
可以直接当作"主线程有多忙"的度量。实测中位数：

| 主题 | 渲染 | 编码 | 推送 | `/diag` 延迟 |
|---|---|---|---|---|
| 11 二次元壁纸 | 16ms | 75ms | 56ms | **221ms** |
| 13 明亮HUD | 20ms | 66ms | 67ms | **220ms** |
| 10 赛博二次元 | 16ms | 64ms | 41ms | **173ms** |
| 12 无框 | 3ms | 71ms | 55ms | 124ms |
| 17 玛丽 / 0 仪表盘 | 3/8ms | — | — | 122ms |

#### 根因

不是某个主题的绘制代码特别慢（分段埋点：backdrop 1ms + panels 4ms + cells 4ms ≈ 9ms），
而是**整帧从头到尾连续占着主线程**：渲染 → `toDataURL`（同步 JPEG 编码 60~75ms）
→ USB 推送，合计 **120~165ms** 中间没有一次让出。

主题 10/11/13 每帧都有变化（星光闪烁 / 花瓣飘落 / 扫描线），内容签名每帧不同
→ **永不触发"内容未变则跳过"** → 主线程被持续吃满。
而 12/17/0 经常命中跳过，你就不觉得卡。

#### 修法

在帧的三个阶段之间主动**让出主线程**（`await setTimeout(0)`）：
`yieldToUi()` 插在「渲染之后」「编码之后」两处，把"连续独占 150ms"拆成几小段，
UI 输入/重绘就能插进来。

#### 效果（同一实例、同一套测法）

| 主题 | 改前 | 改后 |
|---|---|---|
| 11 | 221ms | **125ms** |
| 13 | 220ms | **129ms** |
| 10 | 173ms | **126ms** |
| 12（对照） | 124ms | 124ms |

三个"卡"的主题全部降到和其它主题同一水平（≈125ms 基线）。
代价：每帧多两次 `setTimeout(0)`，实测 fps 与 tickMs 无可见变化。

#### 3D 部分（真投影，不是贴图）
| 元素 | 做法 |
|---|---|
| **自转线框地球** | 球面经纬线 → 绕 Y 轴自转 + 绕 X 轴俯视 → `project(x,y,z) = (cx + x*f/(z+f), cy + y*f/(z+f))` 透视投影；赤道环单独加粗 |
| **景深粒子** | 140 个粒子带 z∈[0.15,1]，`1/z` 决定大小/速度/透明度 → 雨丝、雪花、浮尘都有前后层次 |
| **温度数字** | 同一串数字按 10 层偏移叠画 → 立体挤出厚度 |
| **风向罗盘** | 椭圆压扁（ry/rx≈0.35）模拟俯视透视 + 指针按真实风向角旋转 |
| **7 天柱** | 正面 + 顶面 + 侧面三块 → 立方体质感；统一温度轴，柱高可比 |
| **天气图标** | 太阳 = 光晕 + 12 道缓慢旋转的光芒 + 暗面/高光球；云 = 三团叠加 + 暗底；雨/雪/雷各自动画 |

### 移植「边框扫掠（光沿边框环绕）」（2026-10-22）

用户要求把 BambuHelper 门户里那个**扫掠**效果搬过来（`http://192.168.3.140/#display`）。

#### 参考实现来源
门户页面只是个下拉选项，真实现固件里：
`~/Documents/拓竹P2S开发/bambu-zh/src/display_edge_glow.cpp`
- 周长坐标 q 从左上角顺时针，扫掠头绕周长一圈
- **拖尾长度 = 周长 / 4**，亮度**二次方衰减**（原注释：*brightness fades quadratically over the tail*）
- 每帧重画四条边框条带（面板 30fps）

#### 移植到 ArkTS（`Overlay.sweepBorder`）
做法不同但等效：把"拖尾区间"按四条边切成至多 8 段，
每段用**线性渐变描边**（渐变两端就是该段两端的衰减亮度），
所以整条拖尾连续平滑，每帧只有 8~16 次 stroke，成本很低。

三层叠加：
1. 静态细边框 alpha 0.10（读得出"这是一圈边"）
2. 彩色拖尾：宽晕光（alpha 0.28）+ 主体亮线
3. **白热核心**：只在头部前 150px
4. **头部光斑**：46px 径向渐变光点（低帧率下也能一眼看到头在哪）

#### 与参考的差异（因帧率）
原面板 30fps；这边画布只有 ~3fps，若按参考速度头每帧会跳 400+px，看着一格一格蹦。
所以：**一圈放慢到 12 秒**，并把描边加粗到 7px。

#### 开关
```bash
curl 'http://127.0.0.1:54546/set?sweep=0'   # 关
curl 'http://127.0.0.1:54546/set?sweep=1'   # 只天气主题（默认）
curl 'http://127.0.0.1:54546/set?sweep=2'   # 所有主题都开
```

#### 实测
```
边缘最亮像素 rgb(228,255,255)，扫掠头沿边移动并绕回起点（连续 5 次采样位置各异）
render 7.8ms（含扫掠），fps 2.97，errors=0
```

#### 扫掠参数化（用户拍板 12 秒）
```bash
curl 'http://127.0.0.1:54546/set?slap=12000'   # 一圈时长 ms（2000~60000），默认 12000
curl 'http://127.0.0.1:54546/set?sthk=7'       # 线宽 px（2~16），默认 7
curl 'http://127.0.0.1:54546/set?slap=20000'   # 想更慢就加大
```
实测校验：隔 3 秒抓两帧量头部位移 = 1191px，理论 `周长 4764 ÷ 12s × 3s = 1191px` ✅ 完全吻合。
