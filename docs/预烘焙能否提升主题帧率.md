# 预烘焙能否提升主题帧率？（实测结论）

> 问题来源：会话"利民副屏视频推流可行性"里的**预烘焙**手法，能否用到我们的主题上提升帧率？
>
> 结论先说：**能，但收益的位置和直觉不同**。预烘焙真正省下的是**编码**（71ms/帧）；
> 而我们主题的实际卡点里，**有一半是"帧间隔被白白加了一整段"** —— 那个问题不需要预烘焙，
> 加一个 `burst` 开关就解决了，实测 **5.06 → 15.1 fps（3 倍）**。

## 一、先看实测数字（2026-10-14，真机屏 0416:5408）

### 主题每帧成本分解

| 主题 | 帧字节 | 写次数 | render | encode | push | 字节换算出上限 | 实测 |
|---|---|---|---|---|---|---|---|
| 14 NanoMuse 大字 | 35.2KB | ~9 | 5ms | 71ms | — | 18.1fps | 5.4fps |
| 15 trofeo-lcd | 40.7KB | ~11 | 5ms | 71ms | — | 15.0fps | 4.9fps |
| 0 仪表盘 | 37.6KB | ~10 | 5ms | 71ms | — | 16.4fps | 4.9fps |

**矛盾点**：字节数换算出的上限是 15～18fps，实测只有 5fps。差在哪？

### 找到了：帧间隔是"额外加"的

`tick` 的实现是 `tick → 推帧 → setTimeout(间隔) → tick`，
**间隔加在推帧耗时之外**：

```
fps=8（间隔 125ms）时：
  实测每帧 = render 5 + encode 71 + push 66 + 间隔 125 = 267ms  → 3.7fps
  （`tickGapMs` 实测 198~211ms 印证了这一点）
```

`docs/预烘焙序列.md` 里序列那边用 `seqburst`（间隔压到 1ms）解决的**正是同一个问题**，
但**主题这条路径一直没做**。

## 二、解法：`/set?burst=1`（间隔扣除耗时）

```ts
// 间隔 = max(0, 目标间隔 − 本帧耗时)，避免"额外白等一整段"
const base = this.forceIntervalMs > 0 ? this.forceIntervalMs : policyMs;
let waitMs = base;
if (this.burst && this.tickStartMs > 0) {
  waitMs = Math.max(0, base - (Date.now() - this.tickStartMs));
}
```

**为什么不是照抄序列的"压到 1ms"**：历史上有一次把 USB 批量端点灌到错误态
（`bulkTransfer` 返回 -1、屏黑、连 `/diag` 都不响应，只能 force-stop 重开），
所以这里用"扣除耗时"而不是"取消间隔"。

### 实测收益（主题 15 + 图片背景）

| 配置 | 帧率 | tickGap | 错误 |
|---|---|---|---|
| `fps=8`（基线，无 burst） | 5.06fps | 211ms | 0 |
| `fps=8` + `burst=1` | **9.89fps** | 101ms | 0 |
| `fps=60` + `burst=1` | 9.9fps（撞 `MIN_PUSH_INTERVAL_MS=120` 地板） | 100ms | 0 |
| **auto + `burst=1`** | **15.1fps** | 67ms | 0 |

**最优组合是 `burst=1` + 不设 fps（auto）** —— 因为策略在 `busy` 状态下自己就是
`INTERVAL_BUSY = 66ms`（≈15fps），这是策略自己的安全值，比硬压 120ms 更合理。

## 三、预烘焙对主题到底能省什么

| 环节 | 现在 | 预烘焙能不能省 | 说明 |
|---|---|---|---|
| render | **2~5ms** | 省不了多少 | 已经是毫秒级，不是瓶颈 |
| **encode** | **71ms** | ✅ **能省掉**（这是它真正的价值） | 序列就是"帧是现成 JPEG，字节原样推出去" |
| push | 43~66ms | ❌ 省不了 | 字节数决定，`4096B/写 × 5.5~6.9ms + 3ms ACK` |
| 间隔 | 100~200ms | ✅ 已被 `burst` 解决 | 不需要预烘焙 |

### 但主题和序列有个本质区别

**序列的内容是预先定好的**（同一批帧反复播），所以"完全跳过编码"成立。
**主题显示的是实时数据**（CPU 占用、内存、网络速率……每一帧数字都在变），
所以：

- ❌ 不能把**整帧**预烘焙（数字变了就要重新编码）
- ✅ 可以预烘焙**不变的那一层** —— 但省下的只是 render（2~5ms），**encode 那 71ms 依然要付**
- ✅ 真正能"完全跳过编码"的场景是：**同一帧字节重发**（内容签名没变时），
  这个机制**我们已经有**（`contentSignature` + `HEARTBEAT_MS`，`skippedFrames` 就是它）

**一句话**：预烘焙对"内容确定的画面"是银弹，对"实时仪表盘"只能省 render —— 而 render 本来就只有 2~5ms。

## 四、真正剩下的优化空间

按收益排序：

| # | 手段 | 预期收益 | 代价 |
|---|---|---|---|
| 1 | **`burst=1`**（已实现） | **5 → 15fps** | 无（0 错误） |
| 2 | 把 `MIN_PUSH_INTERVAL_MS` 从 120 降到 ~80 | fps=60 时 9.9 → ~12fps | ⚠️ 有灌爆 USB 端点的风险（历史上出过事故） |
| 3 | **减小帧字节数** | 字节=帧率（`写次数 × 5.8ms + 3ms`） | 降 JPEG 质量或减少高频细节 |
| 4 | 整帧预烘焙 | 只对**静态/循环内容**成立（如像素小游戏、动画 Logo） | 主题的实时数字用不了 |
| 5 | encode 换更快编码器 | 未知 | 鸿蒙的编码器可能不可换 |

### 关于第 3 条的一个反直觉点

主题 15 加**图片背景**看似"多花钱"，实测反而**字节更小**（41.5KB → 25.6~32.3KB）：
那张背景是**低频渐变**，JPEG 压得极便宜；而纯色底 + 大面积文字反而更贵。
→ **"背景图 ≠ 更慢"**，关键看它是不是低频内容。

反过来，**程序化特效背景（plasma/lava/waves）是块状渲染**，块边界是硬边高频，
JPEG 码率会明显上升 —— 这是第 3 条要警惕的方向（待实测确认）。

## 五、结论

1. **预烘焙能提升，但提升点在 encode（71ms），而主题的 encode 省不掉**（内容是实时的）
2. **帧率翻 3 倍靠的是 `burst`**（间隔不再白等），不是预烘焙 —— 这个我们已实现并实测通过
3. **整帧预烘焙只适合"内容确定"的画面**：像素小游戏、动画 Logo、UI 过渡、壁纸动画。
   要在这块屏上做那种内容，就走**序列通路**（`/set?seq=...`），那条路已经完整可用且实测 11~20fps
4. **字节数就是帧率**这个规律依然成立，所以想把主题再提上去，下一步应该压字节（降质量 / 减少高频细节）

## 六、命令与取证

```bash
/set?burst=1        # 极速：间隔扣除本帧耗时（推荐配合 auto fps）
/set?fps=60         # 配合 burst 时会被 MIN_PUSH_INTERVAL_MS=120 地板限制在 ~9.9fps
/set?fps=0          # 回到自适应策略（busy 时 66ms ≈ 15fps）← 与 burst 组合最优
```

`/diag` 取证字段：`burst / tickSpentMs / tickGapMs / forceIntervalMs / fps /
renderMs / encodeMs / pushMs / jpegBytes / skippedFrames`
